feat(calling): Phase 25 S2e - sender-tuning seam + concurrency seams; org.webrtc pins gone from sessions

The two raw org.webrtc touch points (Priority, DegradationPreference) that
blocked any JVM variant of the session classes are now behind an
expect/actual seam in our own module:

- commonMain RtpSenderTuning.kt: AudioSendTuning/VideoSendTuning payloads +
  `internal expect fun RtpSender.applyAudioTuning/applyVideoTuning`. The
  bitrate-priority constants moved here from the sessions' companions.
- androidMain actual: the org.webrtc reach-through moved verbatim
  (RtpSender.android, networkPriority/bitratePriority/degradationPreference).
  minBitrateBps is assigned DIRECTLY (null clears the floor - what the
  concession ladder's non-floor rungs do); other optional knobs skip when
  absent so a concession cannot wipe the earlier tune's framerate cap.
- jvmMain actual: over webrtc-java 0.17's get/setParameters. That backend
  exposes no pacer priority and no degradation preference - logged once per
  process, tuning degrades to the bitrate window (most of the benefit on a
  LAN).

Sessions rewired to the seam; FlashCallSession/FlashGroupCallSession carry no
org.webrtc imports any more.

api(libs.webrtc.kmp) moved androidMain -> commonMain: the phase file's own
condition - "legal once the vendored fork supplies a JVM variant through
substitution" - is met. The F1/ERROR-049 wall is formally gone.

PlatformMonitor (expect + two byte-identical JVM-family actuals, the
core:common PlatformLock pattern duplicated per R2) with SyncList/SyncMap -
lock-guarded commonMain stand-ins for CopyOnWriteArrayList/ConcurrentHashMap,
written for the session-file move that follows.

Also: the fork's CameraPermissionException/RecordAudioPermissionException
moved to its commonMain (plain Exception subclasses) so common code can catch
them; group-call GroupLeg pendingIce retains ArrayDeque (common).
