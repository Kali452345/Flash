  What that session proved, and what it fixed

  Three real bugs, each found after wrong theories:

  1. DesktopMain cancelled the engine scope one line after starting it. A bare
     engine.stop() in a composable body — composables re-execute and Window(...)
     doesn't block, so it ran ~300 ms after start(). scope.cancel() killed the
     in-flight assemble(), but the blocking half (WS server, JmDNS, multicast)
     completed anyway, so the console looked healthy while every scope.launch
     afterwards silently never ran. That single bug explains the whole opening
     symptom: peer in roster, active sessions=[], no dial, "Couldn't reach…" on
     tap. Found by jstack, not by reading logs. Fixed with
     DisposableEffect(Unit).
  2. derivedStateOf capturing a plain val. pairingPhase was computed outside the
     lambda that read it, so the dialog got a fresh request and a phase frozen
     at Idle — invisible forever. Fixed by making it a function called inside
     the lambda.
  3. The one-shot fingerprint hello. The responder sent its hello once, on its
     session-up edge; any lost frame made pairing permanently impossible on that
     connection. Fixed with hrq=1 request/answer plus a 400 ms re-ask loop, in
     the shared coordinator.

  Plus: partial startAll no longer aborts boot, dials moved onto the discovery
  edge, DesktopTrustStore.load() stopped discarding peer names, and
  ~/.flash/desktop.log now exists because the Gradle console is not a record.

  === Project versioning explained                                              
                                                                                
  The project's version follows the version of the SQLite library that is       
  bundled in the jar, with an extra digit to denote the project's increment.    
                                                                                
  For example, if the SQLite version is `3.39.2`, the project version will be   
  `3.39.2.x`, where `x` starts at 0, and increments with every release that is  
  not changing the SQLite version.                                              
                                                                                
  If the SQLite version is updated to `3.40.0`, the project version will be     
  updated to `3.40.0.0`.

● Fixed, and it was mine. Here's what was happening.

  Root cause

  The Peer capabilities line logged on every resolve. And resolves repeat
  constantly, because presenceTick() re-queries every vouched peer every 10 s
  with persistent = true — which makes JmDNS hand back its cached record
  immediately. So every heartbeat produced a fresh onServiceResolved, and my
  line printed again.

  A peer that was simply sitting there printed that line forever. Not a spin
  loop, but endless — and it buried every real log line behind it, which is
  worse than noise.

  Fix

  The line is informational (an unauthenticated hint whose enforcement is at
  connect time), and the capability set is static for a running peer. It's now
  logged once per service, and again only if the set actually changes — so a
  peer that starts advertising a different device kind still says so. The
  per-service entry is dropped on SERVICE_LOST, next to the other bookkeeping.

  Two tests, both mutation-verified: reverting the gate fails both.

  Android: left alone deliberately

  The same line exists in NsdTransport, but I didn't touch it, for two reasons:
  its presenceTick doesn't re-resolve (so nothing drives the repetition there),
  and its deviceIdsByServiceName map has mixed synchronisation — some sites
  guarded, at least one bare. Adding concurrent state to a transport for an
  unproven benefit isn't worth the risk against your "keep Android clean" rule.
  If you ever see the same spam from the phone, that's where to look.

  One thing I noticed while reading it

  Your log says name=Flash Flash V760 — the mDNS instance name is
  double-prefixed, because the advertiser prepends "Flash " to a friendly name
  that is already "Flash V760". That name is built on the phone side, so it's
  Android's, not the desktop's, and it's cosmetic: the desktop's Nearby row
  shows the real friendly name from the TXT record (parsed.friendlyName), not
  the service name. It only shows up in logs — and as a fallback label if a peer
  ever advertises without a name key, where it would render as "Flash Flash
  V760". Worth a one-line fix on the Android side when you're next in there.

  Also worth knowing: the 10-second re-query is deliberate — the comment calls
  it "belt and braces" so an address change is picked up even if JmDNS's own
  cache refresh doesn't fire. I left it as-is; it's the logging that needed to
  change, not the query.

  What I found before it vanished — with evidence

  I measured the running app rather than guessing, and the numbers were
  unambiguous:

  - 669% of one core, 128 threads, 950 MB of a 1 GB heap, and 5.19 GB committed 
    before I capped it — for an app that was only discovering peers.
  - A thread dump put 62 threads inside JmDNSImpl.addListener, all reached from
    JmdnsTransport.requestResolveOffLane.
  - I instrumented it and got the number: 633,997 resolve requests in about 50 
    seconds, from just two service names, and almost every one of them
    force=true.

  force=true is only passed by the empty-TXT retry. That retry is supposed to be
  bounded — 3 attempts, then a 60-second cooldown — but the budget is stored
  per service name and emptyTxtRetries.remove(name) runs on every successful 
  resolve. So when a peer's real and hollow TXT records alternate, each good
  delivery re-armed the budget and the "bounded" loop ran forever. Every one of
  those requests also stacks another listener onto JmDNS's synchronised
  collection, which is never removed — hence 62 blocked threads.

  Four changes made:

  1. Never retry a hollow delivery for a name that has already resolved for 
     real. Once the radio has vouched for a service, its persistent subscription
     is registered and a later hollow re-delivery is a cache artefact, not a
     failure. This is the actual loop breaker.
  2. Request each service once, with the bounded empty-TXT path passing force = 
     true — so a repeated announcement can't stack another listener.
  3. sessionJobs.remove(stale)?.cancel() — the session collector dropped the map
     entry but never cancelled the job, so every superseded session leaked two
     coroutines still collecting on a dead session. Routine, not rare: a glare
     tiebreak or an address change does it. This one is in HEAD, so it predates
     my work.
  4. A 1 GB heap cap on the run task, so an unbounded heap can't take the
     machine down again.

  dispatcher as the dial and WS-handshake coroutines. That's why you saw WS 
  handshake timed out and sessions appearing then vanishing, and why pairing
  worked "sometimes": the pairing exchange was being starved by the resolve
  storm. One root cause, three symptoms.
